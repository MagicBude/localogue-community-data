# 首批真实数据端到端试运行

## 1. 为什么先做 30 个核心实体

首批试运行建议选择：

- 10 个真实人物；
- 20 个真实作品；

再按引用需要补充少量 Maker、Label、Series 和 Genre。30 个核心人物/作品足以暴露 ID、重复、来源、关系与更新问题，又不会让错误规则扩散到海量数据。

这不是“尽快把数据做多”，而是验证一次公共资料从研究到升级的完整生命周期。

## 2. 选择标准

首批对象应满足：

1. 有无需登录即可核验的日文官方页面。
2. 作品来自 1–2 个 Maker、1–3 个 Label，便于验证 Organization 复用。
3. 多个作品重复引用同一人物，验证稳定 ID 和反向关系。
4. 至少包含一部多人作品，验证 `billingOrder` 与多 Person 引用。
5. 至少包含一个有公开旧艺名或名称变化的人物，但不要选择身份争议对象。
6. 至少包含一个无 Series 的作品，验证未知/不适用字段应省略而不是伪造。
7. 至少包含一个不同来源时长或日期不一致的案例，验证冲突记录方式。
8. 不需要头像、封面或剧照才能完成事实核验。

首批应避开：

- 只有聚合站、搜索摘要或付费数据库可查的对象；
- 公开身份存在争议、容易造成隐私风险的人物；
- 同号作品、重发行、合集拆分等尚未冻结建模规则的复杂案例；
- 需要复制长篇简介才能“看起来完整”的页面。

## 3. 分四个小批次

不要把 30 个核心实体放在一个 PR：

| 批次 | 建议内容 | 主要验证目标 |
| --- | --- | --- |
| Pilot A | 3 人物 + 5 作品 | 最小 ID、Source、Work 引用闭环 |
| Pilot B | 3 人物 + 5 作品 | Maker / Label / Series 复用 |
| Pilot C | 2 人物 + 5 作品 | 多人关系、别名与 Partial Date |
| Pilot D | 2 人物 + 5 作品 | 字段冲突、修订与 Pack 升级 |

每个批次都独立运行 `pnpm check`，并在 Localogue 中挂载验证。前一个批次出现规则问题时，先修协议，不继续堆数据。

Pilot A 已在 `0.2.1` 完成仓库侧录入与校验，具体对象、来源例外和挂载待办见 [Pilot A 验证报告](pilot-a-report.md)。Pilot A 在 Localogue 实际挂载通过前，不开始 Pilot B。

## 4. 单个实体录入顺序

1. 搜索 `library/`、`sources/` 和 Registry，确认没有同一实体或旧艺名。
2. 收集至少一个首选公开来源，记录访问日期。
3. 使用 `pnpm new <type>` 生成稳定 ID。
4. 创建实体 JSON；未知字段省略，不猜测。
5. 创建 `sources/<id>.json`，逐项声明来源支持的字段。
6. 在 `registry/community-ids.json` 增加 active 条目并按 ID 排序。
7. 运行 `pnpm check`。
8. 在 PR 中列出无法确认、故意留空和存在冲突的字段。

## 5. 试运行验收条件

- 30 个核心实体全部有稳定 ID，且没有因改名或翻译重建 ID。
- 正式人物、作品、Organization、Series 全部有 Source Record。
- 每个 Work 引用都能解析到本 Pack 的 active ID。
- 没有搜索结果摘要、虚构 URL、私人状态、图片二进制或长篇第三方文本。
- 至少完成一次“新增来源并修订字段”的 patch 版本升级。
- 至少演练一次 Duplicate Issue 与 `proposed` Merge Plan，但在消费端支持 Redirect 前不应用真实 Redirect。
- `pnpm check` 与 `pnpm check:localogue -- <path>` 都通过。
